## 2. NVFP4 scale layout (confirmed, not assumed)

Only `model.layers.{1..47}.mlp.experts.{0..255}.{gate,up,down}_proj` are quantized.
Four tensors per projection:

| tensor | dtype | shape (gate/up) | shape (down) | meaning |
|---|---|---|---|---|
| `weight_packed` | U8 | `[1024, 1536]` | `[3072, 512]` | **E2M1**, two 4-bit codes per byte, K packed 2:1 |
| `weight_scale` | F8_E4M3 | `[1024, 192]` | `[3072, 64]` | one **E4M3** scale per **16** contiguous K |
| `weight_global_scale` | F32 | scalar | scalar | per-tensor FP32 global |
| `input_global_scale` | F32 | scalar | scalar | activation-quant scale — **we do not use it** (W4A16) |

**Group size = 16, confirmed by arithmetic:** `gate_proj` K = 3072, `weight_scale` K-dim = 192,
3072 / 192 = 16. Same as gemma-4. Effective density 4 + 8/16 = **4.5 bits/param = 0.5625 B/param**.

Dequant: `w = e2m1_code · e4m3_group_scale · fp32_global_scale`. Per expert:
3 × (packed + scales) = **5.308 MB**. Whole routed pool = **63.87 GB (88.8 % of the checkpoint)**.

Declining `input_global_scale` is deliberate and inherited from the gemma port: W4A16 (fp16
activations, FP4 weights) dodges vLLM's ~75 µs per-step activation-quant cost at batch 1, and it
is what made gemma's DFlash bit-exact against its own base path.

`model.layers.0.mlp.{gate,up,down}_proj`, `re:.*\.self_attn\.q_proj$`, `k_proj`, `v_proj`,

gap is `embed_tokens`, of which a decode step touches one row). This is
the single most consequential fact in the inventory; see `ROOFLINE.md` §0 and §5.

## 4. KV cache scheme

`quantization_config.kv_cache_scheme`: 8-bit float, `strategy: "tensor"`, `symmetric: true`,
`dynamic: false`. The **static per-tensor scales ship in the checkpoint** as
`model.layers.{N}.self_attn.k_scale` and `v_scale` (BF16 scalars, 48 each). Use them; do not
compute dynamic scales.

## 6. Tokenizer

| | |
|---|---|
| class | `PreTrainedTokenizerFast`, **ByteLevel BPE** |
| vocab | **100 352** ranks, **100 026** merges |
| normalizer | **none** |
| pre-tokenizer | `Sequence` of three stages (below) |
| decoder | `ByteLevel(add_prefix_space=true, trim_offsets=true, use_regex=true)` |
| post-processor | `TemplateProcessing` — prepends `〈\|EOS\|〉` (id 2) as BOS |
| `byte_fallback` | **false** (pure ByteLevel — every byte is already in vocab) |
| `ignore_merges` | false, `dropout` 0.0, no prefix/suffix |
| added tokens | 70, ids 0–69 |

Pre-tokenizer stages, in order:
1. `Split` on `(?:\r?\n)+(?!\r?\n)`, behaviour **`MergedWithNext`** — a run of newlines attaches
   to the chunk that follows it.
2. `Split` on the GPT-4-class regex
   `(?i:'s|'t|'re|'ve|'m|'ll|'d)|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+`,
   behaviour **`Isolated`**.
3. `ByteLevel(add_prefix_space=false, use_regex=false)`.

**Port note.** This differs from gemma-4 in every particular: gemma was `▁`-normalized BPE with
`byte_fallback=true` and a no-op pre-tokenizer. Laguna needs a real Unicode-property regex engine
(`\p{L}`, `\p{N}`) — `std::regex` cannot express these. Plan: hand-rolled scanner over UTF-8
code points with a compact `\p{L}`/`\p{N}` range table, matching the alternation directly rather
than compiling a general regex. `\p{N}` matches **one** code point at a time (no `+`), which
means digits tokenize individually — a detail worth a dedicated test vector.

Notable ids (from `added_tokens_decoder`): 2 `〈|EOS|〉`, 9 `〈|PAD|〉`, **12 `〈|MASK|〉`**
(= the DFlash `mask_token_id`), 18 `<think>`, 19 `</think>`, 23 `<assistant>`,
24 `</assistant>` (special, and an EOS), 25 `<tool_call>`, 26 `</tool_call>`. Brackets are the
**ideographic** `〈` U+3008 / `〉` U+3009, not ASCII `<` `>`.

## 7. Chat grammar (`chat_template.jinja`, read in full)

```
〈|EOS|〉
<system>{system}[\n\n### Tools\n\n…<available_tools>\n{tool json}\n…</available_tools>]</system>\n
<user>{content}</user>\n
<assistant><think>{reasoning}</think>{content}[<tool_call>{name}<arg_key>{k}</arg_key><arg_value>{v}</arg_value>…</tool_call>]…</assistant>\n
<tool_response>{content}</tool_response>\n
```
Generation prompt: `<assistant><think>` when `enable_thinking`, else `<assistant></think>`.

Three findings that shape the server layer:

1. **Tool calls are not JSON.** The wire format is
   `<tool_call>NAME<arg_key>K</arg_key><arg_value>V</arg_value>…</tool_call>`. Values are raw
   strings when the argument is a string and `tojson(ensure_ascii=False)` otherwise. The parser
   must reassemble this into an OpenAI `arguments` JSON object, and the *renderer* must take it
   apart again for history. Round-tripping type information is the subtle part: a value that was
   a JSON number must not come back as the string `"3"`.
2. **Preserved thinking is the default.** With `enable_thinking` true (the shipped default),
   **every** past assistant turn re-renders its `<think>…</think>`. So the server must persist
   reasoning per assistant message and replay it, or the prefix diverges from what the model saw
   and the KV prefix cache misses on every turn. This is exactly the failure mode the directive
   warns about.
3. **A caller-supplied empty system message suppresses the default system block entirely** —
   distinct from omitting the system message, which injects poolside's default text. The API
   must preserve that distinction.

Default system text, verbatim: *"You are a helpful, conversationally-fluent assistant made by
Poolside. You are here to be helpful to users through natural language conversations."*
